### B-e. The three-way split: 432,774, 431,480 and 431,443

All three are the same plan, 109 products ordering 73, counted three different ways. None is a calculation error. Every figure below is reproduced from `backups/tables_20261022T142441Z/data/lp_recommendation.csv` (the plan as it stood before the rounded run, `lp_run` 5) with the formula the code of that time used.

| Figure | What it is | Where it came from |
|---|---|---|
| **431,443** (431,443.01 stored) | The 109 rows of `lp_run` 5, order quantities summed as stored, to two decimals | What the LP solved. Summing `q_i` over the run's rows. |
| **432,774** (432,774.25) | The same 109 rows **plus one run-less accepted row** (recommendation 4, SKIN CARE, 1,331.24 pieces) = 110 rows, summed unrounded | `GET /recommendations`, which counted accepted rows as plan (`PLAN_STATUS_SQL`) until commit `97e564d` made a decided row count only if an LP run produced it. 431,443.01 + 1,331.24 = 432,774.25. |
| **431,480** | The 109 pending rows with **each row's order rounded up to a whole piece, then added** | `GET /dashboard` `reorder_preview.total_order_qty`, which was `sum(whole_units(q_i))` over pending rows (`backend/routers/dashboard.py:2198`), and `whole_units` is a ceiling (`backend/routers/recommendations.py:227`). The frontend's `wholeUnits` is the same ceiling (`frontend/src/utils/formatNumber.js`). 73 non-zero rows rounded up add 36.99 pieces: 431,443.01 + 36.99 = 431,480. |

Why they disagree: **432,774 vs 431,443** is a different row set (110 vs 109); **431,480 vs 431,443** is a different rounding rule (ceiling per row vs none). The 110-row set is the dashboard's pending-only read against `/recommendations`'s all-statuses read; the ceiling is the dashboard card and the Reorder page summing displayed whole pieces. Per-row rounding to the nearest piece gives 431,443 (109 rows) or 432,774 (110 rows), so 432,774 also equals the rounded 110-row total, which is why it looks like a rounding artefact; it is not, it is the extra row.

**Which endpoint served which: reasoned from the code and the backup, not observed.** The old plan no longer exists live (it was overwritten by the rounded run), so I could not call the old endpoints. I checked the arithmetic for every row set against the backup: 109 rows plain 431,443.01; 109 rows ceiling 431,480; 109 rows nearest 431,443; 110 rows plain 432,774.25; 110 rows nearest 432,774; 110 rows ceiling 432,812. That last number is a **fourth** figure the Reorder page would have summed (`ReorderRecommendations.jsx` sums `wholeUnits` over every cycle row), if it listed the accepted row; I did not observe it and the draft does not carry it.

**Now:** `/recommendations`, `/dashboard` `reorder_preview.total_order_qty` and the table all read **435,988**.
