# Audit, 2026-10-23 (kelvin/freeze-package at 492365f)

Read-only. One pass. Nothing here was fixed. Only findings I reproduced are listed (13, ranked by impact).

## How this was run, and its limits

| Item | What was done |
|---|---|
| Target | The real FastAPI app (`backend.main.app`) driven in-process with TestClient against the live Supabase database, over the direct (non-pooler) URL. Read-only SQL used `BEGIN; SET TRANSACTION READ ONLY; ROLLBACK`. |
| Writes | Accept, reverse, propose, approve, reject and direct-apply all ran inside one outer transaction on a single connection, with each request on a savepoint. The outer transaction was rolled back. Checked afterwards on live: `lp_quantity_change` 0 rows, `lp_decision_reversal` 0, `lp_direct_apply_grant` 0, `audit_log` max key 121 (112 rows), the only non-pending recommendation is key 4 (decided 2026-08-24, not mine). |
| Auth | A minted admin token with the session check bypassed (as `scripts/smoke_api.py` does). **Sign-in itself (`POST /auth/login`, 2FA, session row) was not exercised**: it needs a password and writes a session. All five live users are admins, so a non-admin was simulated (user id 99999, `lp.decide` patched in the harness). The permission checks below are real code, the user is not a real account. |
| Timing | Measured from this laptop to Supabase, uncached (the response cache is off under the bypass). Not Render. Render adds its own round trip and the 64 s cold start on record. |
| Not covered | The frontend (labels on the pages were not read except where noted), concurrency (no two-request races were run), Render, email, MFA. |

Not tested (no concurrency run): a planner's INSERT racing an admin's PATCH on the same row.
