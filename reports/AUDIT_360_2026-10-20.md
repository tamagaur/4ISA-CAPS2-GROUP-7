## 5. High: fix before the next adviser review

### BE-1 · Deciding an order removes it from the "current plan"

**Area:** Order plan, all LP cards · **Owner:** Audrey · **Re-checked:** yes (code)

- **Where:**
  - `backend/lp_cycle.py:184-207` (`current_cycle`).
  - Used by `dashboard.py:1057, 1176`, `abc.py:530, 654`, `sku.py:109`, `inventory.py:54` and `policy_comparison.py:167`.
- **Problem:** the "current plan" is the newest cycle that still has **pending** rows, so deciding an order drops that product from the plan:
  - A decided Class A product shows as "no safety stock".
  - Policy comparison leaves it out.
  - The ABC page shows it as "not in the current reorder plan".
  - Once every 2026-03 row is decided, the whole page falls back to the **2026-02** plan, which still has 15 pending rows.
- **Evidence:**
  - The query filters on `WHERE lr.status = 'pending'`.
  - Live: 2026-03 has 108 rows (107 pending, 1 accepted), and policy comparison counts 107.
- **Fix:**
  - Make the current cycle the latest `planning_cycle_date`, or the latest LP run.
  - Read safety stock and reorder point from every status in that cycle.
  - Filter on `pending` only for the "awaiting decision" counts.
- **Check the fix (on a test database):**
  - Accept a Class A row: the safety-stock counts and the policy count stay the same.
  - Decide every row of a cycle: the cycle date stays put.

### FE-1 · Del Monte shows "0 pending reorders, nothing awaiting a decision"

**Area:** Dashboard · **Owner:** Audrey / Kelvin · **Re-checked:** yes

- **Where:** `Dashboard.jsx:1046`, `HeroKpis.jsx:922`, `Charts.jsx:2678`.
- **Problem:** with Del Monte selected:
  - "Pending reorders" shows **0 products** and "Nothing is awaiting a decision".
  - Suggested orders says "No pending recommendations".
  - In fact no order plan covers Del Monte at all.
- **Evidence:**
  - The code does `pendingCount = …product_count ?? 0`.
  - The backend sends `lp.cycle_date = null` and a "does not cover Del Monte" reason, which the card ignores.
  - The Reorder page already words it correctly (`ReorderRecommendations.jsx:1069`).
- **Fix:**
  - When `lp.cycle_date` is null, pass `count={null}` with the backend's reason.
  - Pass `emptyReason` to the Suggested orders widget.
- **Check the fix:** on the Dashboard with Del Monte, both cards say the plan doesn't cover Del Monte; Unilever is unchanged.

### BE-2 · Del Monte class changes count renamed categories as ₱0

**Area:** Dashboard, class-change card · **Owner:** Audrey · **Re-checked:** yes (code)

- **Where:** `backend/marts.py:600-613` (`_unranked_side`).
- **Problem:**
  - A Del Monte category missing from a range only because of the Jan-2025 renaming is counted as **₱0 sales**.
  - So new 2025 categories "enter" from ₱0, and 9 old paths "leave" to ₱0.
  - The 2026-10-16 fix only covers ranges where *nothing* was collected.
- **Evidence:**
  - Live `class-changes?principal=delmonte` (2025 vs 2024) shows 2 new categories entering from ₱0.0.
  - The function's docstring calls a missing category "a real, counted zero", which contradicts CLAUDE.md ("Del Monte: a missing month … never zero").
- **Fix:**
  - For Del Monte, return `(None, "category_absent")` when months = 0.
  - Keep `not_collected` for a range where nothing at all was collected.
  - Pair it with FE-4 on the card.
- **Check the fix:** re-run the call; the comparison revenue comes back null with a reason, and so do the totals.

### DATA-1 · Products that stopped selling still get a forecast

**Area:** Forecast · **Owner:** Yuan / Thea · **Re-checked:** yes (code) · **Needs team sign-off**

- **Where:** `scripts/run_baseline_forecast.py:243-247` (`build_series`).
- **Problem:**
  - A product's sales series ends at its last sales row.
  - For Unilever, months after that with no row (no sale) are dropped instead of counted as zero.
  - So MA3, the accuracy score and the review flag all ignore the recent zero months.
- **Evidence:**
  - `resample("MS")` only covers the first to the last row.
  - 9 `ok` forecasts belong to products with no row in 2026-02.
  - One of them sold nothing for 3 months but is forecast at its old 3-month average and ordered as **critical** (about 2,000 pieces), with no review flag.
- **Fix:**
  - For Unilever, extend the series with zeros up to the latest demand month. Blank captures stay missing, not zero.
  - This changes a recorded rule (CLAUDE.md says `build_series` is unchanged), so it needs the team's sign-off first. See section 8.
- **Check the fix:** in a dry run, that product's MA3 is 0 and no `ok` product's series ends before the latest month.

### DATA-2 · The Unilever demonstration order plan orders 0 for everything

**Area:** Demonstration order plan · **Owner:** Audrey (LP) / Kelvin · **Re-checked:** yes (query)

- **Where:** `scripts/run_lp.py:1033`.
- **Problem:** when the solver returns no plan, the Unilever demonstration run writes **0 for every product**. The real LP writes nothing in that case.
- **Evidence:**
  - `demo.unilever_sku_lp` has 96 rows: **0 ordering, 54 with a positive need** (queried 2026-10-20).
  - It was written 2026-10-16, before the 2026-10-19 solver fix.
  - A dry run today plans 106 non-zero orders.
- **Fix:**
  - Refuse to write, and report the reasons, when there are no orders.
  - Then re-run `run_lp --source demo --principal unilever --write`.
- **Check the fix:**
  - `SELECT count(*) FILTER (WHERE order_qty>0) FROM demo.unilever_sku_lp` returns more than 0.
  - Add a unit test that an empty plan writes nothing.

### SEC-2 · An old sign-in signing key is in the git history

**Area:** Secrets · **Owner:** Maika / Yuan · **Re-checked:** location only

- **Where:**
  - `.env.example` in commit `cd2d26c` (2026-08-22; removed in `c6be910`).
  - README line 187.
- **Problem:**
  - A real `JWT_SECRET_KEY` is in the git history of every team branch.
  - The README says to copy the same `.env` values to Render, so production may sign with a key that's on teammates' laptops or in that old commit.
- **Evidence:**
  - Found with `git log -G`.
  - The old key differs from the current local key (compared by hash, never printed).
  - Render's value is **UNVERIFIED**.
- **Fix:** generate a new production-only key on Render that isn't in any `.env`. Everyone signs in again once.
- **Check the fix:** the Render key matches neither the old commit's key nor any laptop's.

### SEC-1 · The two-step setup step trusts any correctly signed token

**Area:** Sign-in · **Owner:** Maika / Audrey · **Re-checked:** yes (code)

- **Where:** `backend/routers/auth.py:447-488` and `backend/mfa.py:257-276`.
- **Problem:**
  - `/auth/login/setup` and `/setup/confirm` accept any correctly signed "setup" token.
  - They don't re-check the password, whether the role needs two-step sign-in, or whether two-step is paused.
  - So someone holding the signing key (see SEC-2) could sign in as any of the 4 accounts without two-step, with no password.
- **Evidence:** reproduced with a fake database and a throwaway key: forged token → setup 200 → confirm 200 → admin session.
- **Fix:**
  - In both routes, refuse unless two-step is ready, required for the role, and not yet on.
  - Tie the token to a fingerprint of the password hash.
  - Make the token single-use and give it its own key.
- **Check the fix:** re-run the forged-token script; it should get 401 or 503.

- **Rule 2:** no generated row reaches the marts, forecasts, ABC or the LP, and the `demo` schema has no accuracy columns.

- **Real order plan:** no negative orders; the planning mart matches the LP rows and the forecast for all 108 rows; safety-stock and target units are consistent.

### Backend logic

- **All-principals totals:** sums need both principals; weeks of cover uses only principals with a stock count; ABC shares are withheld when both are ranked.
- **Allocation:** compares the same calendar months year on year.
- **Empty and future ranges:** no division by zero, and a blocked reason where data is missing.
- **Writes:** only `lp.decide` / `sku.edit` holders can write, and every write clears the cache.

### Security

- **Tokens:** pinned to HS256, with an 8-hour expiry.
- **Every request** re-checks the account and session. Logout, role change, delete, reset and password change all end sessions.
- **Link tokens:** 256-bit, stored hashed, single-use.
- **Passwords:** hashed with bcrypt. Two-step secrets are encrypted.
- **SQL injection:** none found; request values are always bind parameters.
- **Allowed websites (CORS):** limited to a fixed list.
- **Errors:** no internal errors are shown to users.
- **Email:** the link host comes from configuration, and names are escaped.
- **Supabase Data API:** locked; anonymous users can read 0 of 40 public tables.

### Frontend

- All 44 API paths and their field names match the backend.
- Every main page ignores out-of-date responses, except SKU Management (FE-2).
- Del Monte's unavailable cards show the backend's reason, not 0, except FE-1.
- Sales arrows are green going up and red going down.
- A 401 signs out, and a 403 refreshes permissions.
